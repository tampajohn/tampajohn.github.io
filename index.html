Thesis

A demo is a prompt.
A platform is a set of decisions.

Every enterprise has an impressive AI demo. Almost none survive contact with production — because the model was never the hard part. The hard part is a chain of unglamorous engineering decisions: which protocol, which providers, how to drive adoption, how to structure context, how to evaluate models, and how to measure all of it. Here are the six we made.

01

Choose a protocol

Before picking models, pick the contract everything speaks — we standardized on the Anthropic Messages API, and it compounded from day one.
Section one. The least discussed, most consequential decision. Not "which model" — "which interface."
01 · Protocol

One agreed-upon protocol, everywhere

  • We chose the Anthropic protocol — the Messages API — as the internal standard. Not a model choice: an interface choice.
  • Everything speaks it. Claude Code and our agent harnesses, internal services, notebooks, CI automations — one request shape, one streaming semantics, one tool-use contract.
  • Agents are protocol-native. Our agentic tooling works out of the box because the protocol is the agent contract — tool use, multi-turn, system prompts.
  • The payoff is optionality. Once everything speaks one protocol, any provider that can speak it is a config change — that unlocks section 02 and section 05.
John Adams · ACM Tampa Bay01 · Protocol
Analogy for the room: this is the JDBC/ODBC decision for LLMs. Boring, standard, and the reason everything else got cheap. You're not locking in a vendor — you're locking in a contract.

02 · Multi-provider

Routing: match the provider to the leverage

  • Not every task deserves a frontier model. Routine extraction, triage, and mechanical subagent work runs on open-weights models at a fraction of the cost.
  • Reserve frontier models for high-leverage judgment — adversarial verification, architecture review, ambiguous calls.
  • Tiered pipelines beat single-model pipelines. Our automated PR review: fast model triages → mid model reviews → frontier model verifies before anything is posted.
  • Routing is policy at the proxy, not hope in a prompt.
John Adams · ACM Tampa Bay02 · Multi-provider
Mental model: spend intelligence where it compounds. A triage decision is worth cents; a wrong review posted on a colleague's PR costs trust. Price the task, then pick the provider.

04

Structure the context

Agents are only as good as their context · make it prunable, shareable, and real-time — files are a good place to start, not the destination.
Section four. Most "the model is dumb" complaints are really "the context was empty." But context design has its own requirements.
04 · Context

Three requirements: prunable, shareable, real-time

  • Prunable. Stale context is worse than no context — it confidently misleads. Structure context so old rules, dead decisions, and expired workarounds can be cut cleanly.
  • Shareable. Context is a team asset. Ours lives in the monorepo as reviewed code — CLAUDE.md files, domain rules, checklists — so one engineer's hard-won lesson becomes everyone's context.
  • Real-time. Static files go stale the moment the system changes. The destination is live memory — what we call IMEM — context that updates as the system learns.
  • But start with files. Plain markdown in the repo gets you 80% of the value on day one, and it's the substrate the real-time layer builds on.
John Adams · ACM Tampa Bay04 · Context
The progression matters: files first (today, zero infra), then shareability via the repo, then real-time memory as the system matures. Prunability is the requirement everyone forgets — design for deletion.

05

Evaluate alternative models

One agreed-upon protocol means you can talk to anything that speaks it — and open weights open a second door: composition over monolithic fine-tunes.
Section five. This is where decisions 01 and 02 pay off — model evaluation stops being a migration and becomes an experiment.
05 · Alternative models

The protocol is the evaluation harness

  • Talk to anything in-protocol. Because every workload speaks one protocol through the proxy, evaluating a new model — open-weights or hosted — is routing traffic, not rewriting code.
  • Shadow and A/B by policy. Send 5% of one pipeline node's traffic to a candidate model; compare on the same telemetry. No app changes, no migrations.
  • Adversarial validation. One model attacks the output in parallel subagent passes; a stronger model verifies every finding against reality. Only confirmed results count.
  • Open weights earn their place. Kimi / GLM-class models now carry routine coding-subagent and extraction work — promoted by measurement, not vibes (section 06).
John Adams · ACM Tampa Bay05 · Alternative models
The punchline of the whole architecture: "should we try model X?" went from a quarter-long integration project to an afternoon of routing policy. That's what a protocol buys you.
05 · Alternative models

LoRA thinking: compose, don't monolith

The instinct is to fine-tune one large model to do everything. We went the other way: many small adapters, composed.

  • Small, single-purpose LoRA adapters — one per task family or convention set. Each is cheap to train, cheap to eval, cheap to roll back.
  • Merge without retraining. Techniques like DARE-TIES — drop-and-rescale, then sign-election merging — combine the skills of multiple fine-tunes into one set of weights, sidestepping catastrophic interference.
  • Composition is the routing layer's job. The proxy picks base model + adapter composition per workload — the same policy mechanism as provider routing, one level deeper.
  • Why not one big fine-tune? One artifact, one point of failure, untestable per-skill, and stale the week after training. Composition keeps every skill independently evaluable.
John Adams · ACM Tampa Bay05 · Alternative models
For the ML folks: DARE drops most delta parameters and rescales, TIES resolves sign conflicts before merging — together they let you merge adapters trained independently. For everyone else: LEGOs, not marble. Each piece testable, swappable, pruneable — same philosophy as the context layer.
06

Measure everything

Hell, we're a measurement company — if the AI platform isn't instrumented like a product, it isn't a platform.
Final section — the one with our company DNA in it. VideoAmp measures advertising for a living; we hold our AI systems to the same standard.
06 · Measurement

Instrument the system, not the leaderboard

  • Per-node telemetry on every pipeline. Cost, latency, failure mode, and recovery rate per pipeline node — the proxy makes this free.
  • Evals gate promotion. A model, adapter, prompt, or pipeline change ships when the eval suite says so — same discipline as a schema migration.
  • System metrics over model benchmarks. We don't ask "is this model good?" We ask "did this node's failure rate drop?"
  • Meta-measurement. The meta-loop measures the reviewers themselves — repeated findings, false claims, drift — and files its own fixes.

What this enabled

Self-improving PR review
  • The review loop measures itself — 4 misbehavior detectors on a 6-hour meta-loop
  • Investigates its own failures in worktrees, opens its own fix PRs
  • Gets quieter as it gets smarter — findings deduped, raised once, not forever
Vampflake: our own query engine
  • A distributed query engine — Rust on the Arrow ecosystem (DataFusion)
  • One binary, three deployable units — API, worker, UI
  • A build that used to require a vendor or a very large team — done by a small team amplified by agents
Retired legacy subscriptions
  • Internal agent-built tools replaced legacy enterprise SaaS
  • Build-vs-buy flips when building gets an order of magnitude cheaper
  • Every retired subscription funds the next internal platform

The compounding part: each of these makes the next one cheaper. The platform builds the platform.

Takeaways

The six decisions, portable edition

  • Pick a protocol before a provider — the contract is the leverage.
  • Put a proxy in front of everything — routing, auth, and telemetry in one place.
  • Drive adoption with running systems — show the art of the possible; build trust mechanics, not mandates.
  • Structure context to be prunable, shareable, real-time — and start with plain files.
  • Evaluate models through the protocol — and compose small LoRA adapters instead of one monolithic fine-tune.
  • Measure everything — per-node, system-level, continuously. (Hell, we're a measurement company.)
